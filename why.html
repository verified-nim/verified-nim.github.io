Why compiler-verified skills leave less to review in your agent’s Nim

Your agent can write its own Nim guidance or read the docs, and both read well. The compiler has run neither. Verified Nim Skills is guidance the compiler has already checked, so your agent does the work a careful Nim engineer would, the same way every run, and you have less to check in review.

The problem: Nim that passes and still needs a careful reviewer

Code models are weaker on low-resource languages, and Nim is one.9 Strong models still write Nim that builds and passes its tests. What they leave out is the work a careful Nim engineer adds: a trimmed and confirmed reproducer, a record of the bug a port inherits, one validation at the trust boundary. Your review has to ask for it, run after run.

Guidance can close that gap only if the guidance is right, and Nim’s sharpest rules are where fluent advice goes wrong. The dangerous mistakes compile: ownership hooks that crash on legal reuse, copy guards that miss aliasing, fuzz harnesses that die on an empty input. They pass the happy-path test and fail in production.

An agent cannot catch these by reading. Someone has to run the code. See three real examples →

Self-written skills don’t check themselves

Claude Code and Codex both ship skill creators.1 The output reads well. It is not verified.

SkillsBench measured this directly. Curated skills raised task success by about 16 percentage points. Skills that models wrote for themselves gave no average gain.2 In the authors’ words, models “cannot reliably author the procedural knowledge they benefit from consuming.”

Generated skills improve only with a test loop.3 For Nim, that loop means test programs run against the real compiler, in debug and release, re-run on every new build. That loop is our product.

Our own carefully written drafts needed a correction or a caveat on about one claim in four. A self-generated skill carries the same kind of errors, unchecked. The checking shows up in agent results too: on three tasks, the unverified draft of each skill passed 1 of 3 runs and the verified skill passed 3 of 3.

Docs say what exists, not what is safe

Context7 indexes Nim and Nimony, and nimlangserver has an MCP mode.8 Keep them. They answer “what API exists”.

They don’t answer “will this crash”. No doc page lists compiler bugs nobody has found yet. Our verification found one, a release build that silently drops errors, and got it fixed upstream. Docs also don’t tell the agent how a careful engineer works: when to confirm a reproducer, where to validate, what to record. Raw docs add the context volume the studies below warn about.

Consistent work, less to review

Verified guidance changes what arrives in your review. In a blind, pre-registered benchmark on DeepSeek V4.1 Flash and GPT-6.1 Sol, runs passed every check 56 of 57 times with the skills and 18 of 59 without, at both maximum and low reasoning effort.

Correctness was level: 74 of 75 scored runs with the skills and 77 of 77 without passed every correctness check. The difference is the work a reviewer would otherwise ask for:

  • Without the skills, not one run on either model stated a reproduction rate in its bug report.
  • No run without the skills recorded the C defect a port deliberately keeps.
  • Without the skills, error-handling code checked data the compiler had already checked, in every run at three of the four model and effort settings.

More reasoning does not stand in for the skills. At low effort with them, DeepSeek V4.1 Flash passed 14 of 15 runs; at maximum effort without them, 3 of 15. The full results, method and limitations.

Why our skills are small, targeted and tested

Bloated, unverified skill packs make agents worse:

  • In SkillsBench, focused sets of two or three skills beat comprehensive bundles, which came out slightly negative. 16 of 84 tasks got worse with skills.2
  • An ETH study found generic context files raised inference cost by over 20% without improving success.4 Model quality also drops as input grows.5

Each of our skills covers one topic, so the agent loads one or two, not twenty. Every edit is evidence-gated: we tighten or delete before we add. Trimming one verified skill that made agents over-measure cut mean agent time per task by 44%, at the same pass rate.

Skills also have to load. Agents skip unforced skills often,67 so onboarding includes a two-line AGENTS.md pointer that tells the agent to load them.

What the skills do to cost

Buy the skills for the quality of the work. On workflow-heavy tasks a run does more work, so it often costs more: the agent trims the reproducer, records the defect, runs the sanitizer. It also finishes far more often, so each passing run costs less. For DeepSeek V4.1 Flash, cost per passing run was 35% lower at maximum effort with the skills and 46% lower at low effort. See the cost results.

An earlier study on four hard Nim tasks points the same way. With our skills, a low-cost model passed 18 of 20 runs; without them, 3 of 20. Each skill-guided attempt used about twice the tokens, and each solved task cost about $0.05 instead of $0.21. On the one task the model already coped with, the skill added about 30% cost for a gain that was not statistically significant.

A bigger model is no shortcut to the same work. Claude Opus 5.5 lists at $4 input and $20 output per million tokens;11 DeepSeek-V4-Flash-class models list at about $0.14 and $0.28.10 On the same four Nim tasks, GPT-6.1 Sol at maximum reasoning effort passed 1 of 12 runs without skills and 9 of 10 scored runs with them (two skill runs blocked by the provider’s content filter were not scored). And no model, however large, has seen the compiler build you installed last week. Published work points the same way: smaller models with good skills compete with larger models without them.26

Why a subscription, not a download

Compilers move, and correct guidance goes stale without anyone touching it. A moved library path broke all 12 tests of one skill during our own verification. Newer rules required an explicit std/syncio import. An API a skill named had been renamed.
