With the skills, 56 of 57 runs passed. Without them, 18 of 59.

Both arms wrote Nim that works. With Verified Nim Skills, agents also did the work a reviewer asks for: trimmed and tested reproducers, ported defects on record, validation once at the trust boundary, and a sanitizer setup that reports every fault. That holds on DeepSeek V4.1 Flash and GPT-6.1 Sol, at maximum and at low reasoning effort. On the control tasks, which agents already pass on their own, pass rates stay level.

Results

Seven private Nim tasks cover bug reporting, porting, error handling, ownership hooks and debugging. Five separate agents with and without the skills; two are control tasks. Every task ran three times per model, reasoning effort and arm, blind, in a fresh sandbox. A run passes when every check passes.

Lift is the difference in pass rate, pooled across tasks (a Mantel–Haenszel risk difference), so it can differ slightly from the raw totals. p is a stratified permutation test. A run the provider stopped, by a content-filter refusal or a usage limit, is retried once and otherwise left unscored, which is why some GPT-6.1 Sol cells have fewer than 15 runs. At maximum effort GPT-6.1 Sol covers 5 of the 7 tasks: the debugging task has 2 scored runs per arm, and the control tasks were not run.

More reasoning does not stand in for the skills. At low effort with the skills, DeepSeek V4.1 Flash passed 14 of 15 runs; at maximum effort without them, 3 of 15. GPT-6.1 Sol passed 14 of 14 at low effort with the skills and 5 of 14 at maximum effort without them.

Correctness is level. Across both models and both effort levels, 74 of 75 scored runs with the skills and 77 of 77 without passed every correctness check, such as the build, the tests and output parity. The lift is in workflow and code quality.

What the skills change

An independent audit labelled every check. A defect check catches an observable fault or a broken requirement of the task. A quality check measures a property of the code or report. A convention check looks at wording and markers. These are the checks that runs without the skills failed:

In plain words: without the skills, bug reports arrived with untrimmed reproducers and no reproduction rate. Ports matched the C tool’s output but left its preserved defect unrecorded. Error-handling code checked compiled-in data a second time. And the debugging scripts let Nim’s own crash handler swallow segmentation faults, so AddressSanitizer never printed its report. On the container with ownership hooks, both arms passed every run.

With the skills, one check failed across all 57 separating runs: a DeepSeek V4.1 Flash report at low effort left out the Nim version. For the error-handling result in depth, read stop your agent validating trusted data twice.

How we test

  • Pre-registered. Tasks, arms, models, metrics and the analysis were written down, and the task set frozen by hash, before the first run. The low-effort rerun was pre-registered separately, before its first run, on the same frozen tasks.
  • Blind, sandboxed runs. Each run starts in a fresh sandboxed workspace with no context files and with network access, as real agents have. In the skill arm, the skill is mounted read-only and the agent must read it. Runs that fetch published skill material are flagged; none were.
  • Control tasks. Two tasks that agents already pass check that the skills do no harm.
  • Scripted checks with independent labels. Each task has a deterministic judge with named checks, and an independent audit labelled every check as correctness, defect, quality or convention.
  • Infrastructure failures are not scored. A timeout, provider error or empty reply is retried once; a run that still fails is reported as unscored and never counted as a pass or a fail.
  • Deviations disclosed. Two changes followed the pre-registration. The pooled lift is a Mantel–Haenszel risk difference in place of an odds ratio, because odds ratios are undefined when a cell is all-pass or all-fail, which is common at three runs. And the without-conventions measure above was added post hoc.

Limitations

  • Three runs per cell. Per-task intervals are wide. The pooled lift across tasks is the claim; single-task numbers are indicative.
  • Seven tasks, designed in-house. The team that writes the skills also wrote the tasks. The separating tasks were chosen because they separate, so their lift is an upper bound for skill-relevant work and does not estimate Nim coding in general. The independent label audit and the frozen task hashes limit this bias. Task text is withheld so the benchmark stays uncontaminated.
  • Two models. DeepSeek V4.1 Flash and GPT-6.1 Sol, the two named in the pre-registration, at two reasoning efforts. Providers change models over time, so every run is dated.
  • Partial GPT coverage at maximum effort. GPT-6.1 Sol covers 5 of the 7 tasks there, with 2 scored runs per arm on the debugging task and no control runs. At low effort it covers all 7.
  • One post-hoc measure. The lift without convention checks was defined after the first results, and is labelled as such.
  • Costs for one model. Only DeepSeek V4.1 Flash has API-priced runs.

Probes across the catalog. On 12 of 17 skills, the agent without the skill failed a check that the skill-guided agent passed (one run per arm). The failures included a use-after-free under self-assignment aliasing, C-library build configuration that only works on one machine, fuzz harnesses missing required flags, and test runners that silently skip new tests.

The compiler audit

This evidence does not depend on agent behavior at all.

  • 912 claims across 21 skills, checked against Nim 2.3.1 or Nimony 0.6.3. 783 are testable by a program; the rest are process advice.
  • 690 compiler-run test programs back the testable claims.
  • 127 corrections to the first drafts, about one in seven claims, and 104 claims given a precise caveat: right in the common case, wrong at an edge an agent will reach.
  • 7 Nimony compiler bugs in error handling (#2674–#2680); four lost errors silently or crashed. Upstream fixed them within two days, and the fix changed a .raises rule the error-handling skill taught, so the next test run flagged the sentences to rewrite.
  • Auditing the Nimony assembler skill found further toolchain bugs, including a silent miscompile. Some are public as #2686 and #2687.

A skill file repeats its mistakes in every run that loads it, so one correction fixes every later run. Two corrections in detail: why a moved-from object segfaults on reuse and the Nimony release build that swallowed the error.

Notes on the earlier studies

  • The three-arm trials are n=3 per arm; the cost study is n=5 per arm; the frontier check is n=3 per arm; catalog probes are n=1 per arm.
  • Cost-study tasks were chosen because they had separated before, so their pass-rate gaps are an upper bound. The cost study used one model family; the frontier check used one frontier model.
  • Two three-arm results come after a revision, one to the skill and one to the scorer. Before it, the verified skill scored 2/3 on each.
  • Some probe separations only show that the agent adopted a convention the skill teaches.
  • On one doc-comment probe the verified skill scored 2/3 against 3/3 without it.

Stronger models will solve more tasks unaided. We track that and prune guidance that stops helping, which keeps the skills small.
