What changes in your agent’s work

Without guidance, both models still wrote Nim that builds, passes its tests and matches the expected output. What they skipped was the work a reviewer then has to ask for. The skills put that work back into the agent’s own routine.

Bug reports a maintainer can act on

Without the skills, reports arrived with untrimmed reproducers and no word on how often the failure happens. Not one run on either model stated a reproduction rate. With the skills, the agent cuts the reproducer to the minimum, runs it to confirm it fails every time and quotes the Nim version and the failing output.

Ports that put inherited bugs on record

A port from C matched the original tool’s output in both arms. Without the skills, no run recorded the C defect the port deliberately keeps, so the next maintainer finds it the hard way. With the skills, the defect is on record in the code and in the porting notes.

Validation once, at the trust boundary

Without the skills, error-handling code checked data the compiler had already checked, in every run at three of the four model and effort settings. With the skills, the agent validates untrusted input once, where it enters, and trusts what the build already proved. Stop your agent validating trusted data twice shows the pattern in code.

A sanitizer setup that reports every memory fault

Without the skills, the debugging scripts let Nim’s own crash handler swallow segmentation faults, so AddressSanitizer never printed its report. That happened in every DeepSeek V4.1 Flash run without the skills, at both effort levels. With the skills, the sanitizer sees the fault and reports it.

With the skills, one check failed across all 57 separating runs: a low-effort DeepSeek V4.1 Flash report left out the Nim version. On the fifth task, a container with ownership hooks, both arms passed every run.

Behind each behavior is a skill file the compiler has checked. Every code claim in the catalog is a program that the current Nim or Nimony compiler builds and runs, and the tests run again when the compiler changes. What the compiler audit found.

The evidence: a blind Nim benchmark on two models

Five private Nim tasks measure the quality of AI-written Nim on the work above: bug reporting, porting, error handling, ownership hooks and debugging. Each ran three times per model, effort level and arm, blind, in a fresh sandbox. A run passes only when every check passes.

Runs that passed every checkWith skillsWithout skills
DeepSeek V4.1 Flash, maximum effort15/153/15
GPT-6.1 Sol, maximum effort13/135/14
DeepSeek V4.1 Flash, low effort14/153/15
GPT-6.1 Sol, low effort14/147/15
Total56/5718/59

Every gap is statistically significant (stratified permutation test, p ≤ 0.0011; pooled lift between +0.51 and +0.80). A run the provider stopped, by a content-filter refusal or a usage limit, is retried once and otherwise left unscored, which is why some GPT-6.1 Sol cells have fewer than 15 runs. At maximum effort, GPT-6.1 Sol covers 5 of the 7 tasks.

Low effort with the skills beats maximum effort without

More reasoning does not stand in for the skills. At low effort with them, DeepSeek V4.1 Flash passed 14 of 15 runs; at maximum effort without them, 3 of 15. GPT-6.1 Sol shows the same pattern in the table above.

No change where no change was expected

Two control tasks, which agents already pass on their own, check that the skills do no harm. Pass rates on them stayed level with and without the skills. The one miss was a low-effort DeepSeek V4.1 Flash run with the skills that built a JSON writer failing the basic output check, the only run in either arm that failed a correctness check. GPT-6.1 Sol did not run the control tasks at maximum effort.

Beyond formatting, the gain remains

Some checks look only at conventions, such as the port’s defect record and the report’s field order. Remove every one of them, and the skills still lift both models at both effort levels, with a pooled lift between +0.31 and +0.60 (p ≤ 0.0186). We added this measure after the first results came in, and report it as post hoc.

Questions developers ask

Don’t strong models already know Nim?

They know how to write correct Nim. Across both models and both effort levels, 74 of 75 scored runs with the skills and 77 of 77 without passed every correctness check: the build, the tests and output parity. The skills add the part a correctness check never asks for: the workflow and code quality of a careful Nim engineer.

Is the benchmark cherry-picked?

The tasks, models, metrics and analysis were written down before the first run, and the task set was frozen by hash. Two control tasks check for harm, an independent audit labelled every check, and the limitations are published with the results. The separating tasks were chosen because they separate, so their lift is an upper bound for skill-relevant work, and we say so.

Do the skills make the agent cost more?

On workflow-heavy tasks a run does more work, so it often costs more: the agent trims the reproducer, records the defect, runs the sanitizer. It also finishes far more often, so each passing run costs less. For DeepSeek V4.1 Flash, the one model here billed per API token, cost per passing run was 35% lower at maximum effort with the skills and 46% lower at low effort.

The cheapest passing run came from low effort with the skills, at $0.039 against $0.147 for maximum effort without them.

How we test

  • Pre-registered. Seven tasks, two models, two effort levels and the analysis were fixed in writing, with the task set frozen by hash, before the first run.
  • Blind and sandboxed. Each run starts in a fresh workspace with no context files. In the skill arm the skill is mounted read-only and the agent must read it.
  • Scripted checks. A deterministic judge scores each task with named checks, and an independent audit labelled every check as correctness, defect, quality or convention.
  • Controls and clean scoring. Two control tasks test for harm. A timeout, provider error or empty reply is retried once and otherwise reported as unscored, never as a pass or a fail.

Limitations

  • Three runs per cell. The pooled lift across tasks is the claim; single-task numbers are indicative.
  • The tasks are designed in-house and their text is withheld, so the benchmark stays uncontaminated. The frozen task hashes and the independent label audit limit the bias, and the result measures skill-relevant work, not Nim coding in general.
  • Two models at two reasoning efforts, the two named in the pre-registration. Providers change models over time, so every run is dated.
  • At maximum effort, GPT-6.1 Sol covers 5 of the 7 tasks, with 2 scored runs per arm on the debugging task and no control runs. At low effort it covers all 7.
  • Two disclosed deviations from the pre-registration: the pooled lift is a Mantel–Haenszel risk difference in place of an odds ratio, which is undefined when a cell is all-pass or all-fail, and the lift without convention checks was added post hoc.
  • Costs are priced for DeepSeek V4.1 Flash only.

Earlier studies

Three earlier, smaller studies point the same way. Their numbers stand as published.

Cost study: 18 of 20 with the skill, 3 of 20 without

A pre-registered study in October 2026 ran four hard Nim tasks, five blind runs per arm, on DeepSeek V4.1 Flash with and without the verified skill. Costs are recomputed from logged tokens at the provider’s off-peak API rates.

  • Per attempt, the skill-guided agent used about twice the tokens (3.1M vs 1.6M) and cost about $0.048 vs $0.028.
  • Per solved task, it cost about $0.05 vs $0.21, about a quarter, because the unguided agent rarely finished.
  • Frontier check. On the same four tasks, GPT-6.1 Sol at maximum reasoning effort passed 1 of 12 runs without skills and 9 of 10 scored runs with them (two skill runs blocked by the provider’s content filter were not scored).
  • Rerun after a model update. When DeepSeek updated V4.1 Flash, the same four tasks passed 11 of 12 runs with skills and 3 of 12 without.
  • On the container task the model already coped; there the skill added about 30% cost for a gain that was not statistically significant.

The compiler audit

This evidence does not depend on agent behavior at all.

  • 912 claims across 21 skills, checked against Nim 2.3.1 or Nimony 0.6.3. 783 are testable by a program; the rest are process advice.
  • 690 compiler-run test programs back the testable claims.
  • 127 corrections to the first drafts, about one in seven claims, and 104 claims given a precise caveat: right in the common case, wrong at an edge an agent will reach.
  • 7 Nimony compiler bugs in error handling (#2674–#2680); four lost errors silently or crashed. Upstream fixed them within two days, and the fix changed a .raises rule the error-handling skill taught, so the next test run flagged the sentences to rewrite.
  • Auditing the Nimony assembler skill found further toolchain bugs, including a silent miscompile. Some are public as #2686 and #2687.

A skill file repeats its mistakes in every run that loads it, so one correction fixes every later run. Two corrections in detail: why a moved-from object segfaults on reuse and the Nimony release build that swallowed the error.

Notes on the earlier studies

  • The three-arm trials are n=3 per arm; the cost study is n=5 per arm; the frontier check is n=3 per arm; catalog probes are n=1 per arm.
  • Cost-study tasks were chosen because they had separated before, so their pass-rate gaps are an upper bound. The cost study used one model family; the frontier check used one frontier model.
  • Two three-arm results come after a revision, one to the skill and one to the scorer. Before it, the verified skill scored 2/3 on each.
  • Some probe separations only show that the agent adopted a convention the skill teaches.
  • On one doc-comment probe the verified skill scored 2/3 against 3/3 without it.

Stronger models will solve more tasks unaided. We track that and prune guidance that stops helping, which keeps the skills small.
