Nim {.raises: [].}: stop your agent validating trusted data twice

  • 18 October 2026

Validate once at the boundary, carry the proof in a distinct type, and mark the code behind it {.raises: [].}.

On this page

  1. The check that can never fire
  2. What a dead error path costs
  3. Validate once, carry the proof
  4. Make the compiler enforce it
  5. Data the compiler already checked
  6. What agents did in two studies
  7. Checklist for your own code

Nim can prove that a proc never raises, yet coding agents fill trusted code with error paths that cannot run: an “unknown unit” raise on a value that already passed validation, a try around a call that cannot fail, a run-time check on a table the compiler already parsed. In two studies, agents without guidance broke this rule in every run.

Verified on Nim 2.3.1. Updated 2026-10-19: added compile-time data and a second study.

The check that can never fire

A command-line tool converts lengths. The user names a unit; the conversion factors are compiled into the binary. This is the shape agents write without guidance:

It compiles, ./before km prints 3000.0 and ./before ft exits with unknown unit: ft. Every test passes. The second “unknown unit” check and the try around toMeters can never run: the only unit that reaches them has already passed parseUnit, and the table cannot change after the build.

What a dead error path costs

No input reaches a dead raise, so no test covers it. Its signature still says the proc can fail, so every caller writes a handler that is dead too. And a reader can no longer tell where bad input is actually rejected.

Validate once, carry the proof

Raise once, where untrusted input enters. Return a distinct type from that check, so the type itself says “this value was validated”, and let everything behind it take only that type:

./after km prints 3000.0; ./after ft exits 1 with unknown unit: ft
import std/os

type Unit = distinct int    # index into Units; only parseUnit makes one

const Units = [(name: "m", meters: 1.0), (name: "km", meters: 1000.0),
               (name: "mi", meters: 1609.344)]
static:                     # a bad table fails the build, not a customer's run
  for u in Units: doAssert u.meters > 0, "bad factor for " & u.name

proc parseUnit(s: string): Unit {.raises: [ValueError].} =
  for i, u in Units:
    if u.name == s: return Unit(i)
  raise newException(ValueError, "unknown unit: " & s)

proc toMeters(u: Unit; value: float): float {.raises: [].} =
  value * Units[u.int].meters

let unit = try: parseUnit(paramStr(1))
           except ValueError as e: quit e.msg
echo toMeters(unit, 3.0)

Same output, one raise, one handler. A raw string no longer fits: toMeters("km", 3.0) is a type mismatch, so unvalidated input cannot reach the trusted path. The static block checks the table during the build, so a zero factor stops compilation instead of a customer’s run.

Make the compiler enforce it

A comment saying “this cannot fail” lasts until the next edit. {.raises: [].} is checked on every build. Add a raise to toMeters, as an agent tidying up “missing validation” would, and the build stops:

(ref ValueError)(msg: "negative length", parent: nil) can raise an unlisted exception: ref ValueErrorafter.nim(16, 17)
proc toMeters(u: Unit; value: float): float {.raises: [].} =
  if value < 0: raise newException(ValueError, "negative length")
                ^

Nim 2.3.1, the file above with one line added. Calling a proc that can raise is rejected the same way.

Data the compiler already checked

The same rule covers data a program ships with. A second tool prices parcels by zone from a CSV file in the repository, parsed with staticRead inside a const, so the parser runs in the compiler:

Those raises run once, during the build. Type a semicolon for a comma on the eu row and nim c after.nim stops:

unhandled exception: rates.csv:3: expected zone,eur_per_kg [ValueError]after.nim(12, 20)
stack trace: (most recent call last)
after.nim(17, 25)
after.nim(12, 20) parseRates
after.nim(12, 20) Error: unhandled exception: rates.csv:3: expected zone,eur_per_kg [ValueError]

Nim 2.3.1, rates.csv line 3 changed to eu;4.50. A rate of -9.80 stops the build with rate must be positive, and 9.8O with invalid float: 9.8O. Paths shortened.

No binary exists with a bad table in it. Agents without guidance re-check it at run time anyway:

It behaves exactly like the lean version: ./before eu 2 prints 9.0. Three raises guard a table the compiler has already checked, and a fourth repeats parseZone. With a Zone type, as in the units example, shippingCost shrinks to kg * Rates[z.int].perKg and the file to 32 lines from 42. Mark the agent’s shippingCost {.raises: [].} instead and the redundant check becomes a compile error:

(ref ValueError)(msg: "corrupt rate for " & zone, parent: nil) can raise an unlisted exception: ref ValueErrorbefore.nim(32, 9)
      if r.perKg <= 0:                        # checked twice already
        raise newException(ValueError, "corrupt rate for " & zone)
        ^

Nim 2.3.1, before.nim with {.raises: [].} added to shippingCost on line 28.

Data the project ships and the compiler parses is already trusted. Its checks belong in the build; run-time checks belong where outside input enters.

What agents did in two studies

Both studies compared agents with and without the verified error-handling skill, on different tasks, so their numbers stay apart.

Study 1, user input: 0 of 11 without the skill, 8 of 11 with it

The task: a multi-module command-line tool that validates uploaded input and compiles its product data into the binary. Runs were blind and sandboxed.

Runs passedVerified skillNo skill
DeepSeek V4.1 Flash, pre-registered study3/50/5
DeepSeek V4.1 Flash, after DeepSeek’s model update2/30/3
GPT-6.1 Sol, maximum reasoning3/30/3
Total8/110/11

The unguided programs mostly produced correct output, but raised errors no input could trigger and handed callers a wider error contract than the program has. GPT-6.1 Sol at maximum effort made the same choice in all three runs.

The task was chosen because it separates agents with and without the skill. Code examples were compiled and run with Nim 2.3.1 on Linux amd64.

Study 2, compiled-in tables: 8 of 8 without the skill re-validated, 0 of 8 with it

The task: a multi-module quote calculator with three bundled data tables compiled into the program. Agents ran sandboxed at maximum reasoning, 8 runs per arm (7 DeepSeek V4.1 Flash, 1 GPT-6.1 Sol). We counted raise and assert sites reachable from the table initialisers in lexed source.

8 runs per armVerified skillNo skill
Runs that re-validated the bundled tables0/88/8
Raise or assert sites per run0 in every run11, 12, 11, 3, 12, 6, 11, 12
Runs that passed every correctness check8/88/8
Held-out DeepSeek trials that re-validated (3 per arm)0/33/3

An exact permutation test on the site counts gives p ≈ 0.0002, and the held-out confirmation on fresh trials split the same way.

Every run in both arms built and passed every check on output, error reporting and API. The difference is the code left behind: in a 5-run subset, the trusted modules came to 55–94 lines with the skill and 96–170 without.

Small sample, mostly one model family. The task stays private for a future leaderboard.

Both results are about code quality; this article makes no claim about cost or speed.

Checklist for your own code

  • Validate command-line arguments, uploads and network input once, at the boundary.
  • Return a distinct type from the validator and make trusted procs take it.
  • Check project-owned data at compile time with const and staticRead, so a bad file fails the build.
  • Delete run-time re-checks of trusted data and mark trusted procs {.raises: [].}.
