Nim staticRead: your agent re-checks data the compiler already checked

  • 19 October 2026
  • Antonis Geralis
  • 4 min read
  • Verified on Nim 2.3.1

When a Nim program parses its own data file at compile time, a malformed file stops the build. Coding agents check the table again at run time anyway, and each check adds a raise path to code that should never fail. Without the error-handling skill, all 8 runs did this, with up to 12 raise or assert sites each. With the skill, all 8 validated once, at the user-input boundary.

This follows stop your agent validating trusted data twice, which covered user input carried in a distinct type. This one is about the data your program ships with.

A malformed table already fails the build

A command-line tool prices parcels by shipping zone. The rates live in a CSV file in the repository, and the program parses that file with staticRead inside a const, so the parser runs in the compiler and the binary carries the finished table:

Those raises run once, during the build. Type a semicolon for a comma on the eu row and nim c after.nim stops:

unhandled exception: rates.csv:3: expected zone,eur_per_kg [ValueError]after.nim(12, 20)
stack trace: (most recent call last)
after.nim(17, 25)
after.nim(12, 20) parseRates
after.nim(12, 20) Error: unhandled exception: rates.csv:3: expected zone,eur_per_kg [ValueError]

Nim 2.3.1, rates.csv line 3 changed to eu;4.50. A rate of -9.80 stops the build with rate must be positive, and 9.8O with invalid float: 9.8O. Paths shortened.

No binary exists with a bad table in it. Whatever reaches run time has already passed every check in parseRates.

What agents add anyway

Agents without guidance treat the compiled-in table like a file read from disk. This is the shape they write after the same parseRates:

It compiles and behaves exactly like the lean version: ./before eu 2 prints 9.0 and ./before mars 2 exits with unknown zone: mars. Three raises guard a table the compiler has already checked, and a fourth repeats parseZone. None of them can fire, so no test covers them, and shippingCost now tells every caller it can fail.

Trust the table, check the user

The real trust boundary is the command line. Validate the zone there, once, return a Zone that only parseZone can produce, and let the pricing code take that type and nothing else:

./after eu 2 prints 9.0; ./after mars 2 exits 1 with unknown zone: marsafter.nim, lines 17–32
const Rates = parseRates(staticRead("rates.csv"))   # runs inside the compiler

proc parseZone(s: string): Zone {.raises: [ValueError].} =
  for i, r in Rates:
    if r.zone == s: return Zone(i)
  raise newException(ValueError, "unknown zone: " & s)

proc shippingCost(z: Zone; kg: float): float {.raises: [].} =
  kg * Rates[z.int].perKg

try:
  let zone = parseZone(paramStr(1))
  let kg = parseFloat(paramStr(2))
  echo shippingCost(zone, kg)
except ValueError as e:
  quit e.msg

It builds without a warning. shippingCost is one line and declares that it cannot raise. The only raises left at run time are the two that a user can trigger: an unknown zone and a weight that is not a number (./after eu two exits with invalid float: two). The whole file is 32 lines against 42 for the version above.

Let {.raises: [].} hold the line

The annotation keeps the next edit honest. Put {.raises: [].} on the agent’s shippingCost and the redundant check becomes a compile error:

(ref ValueError)(msg: "corrupt rate for " & zone, parent: nil) can raise an unlisted exception: ref ValueErrorbefore.nim(32, 9)
      if r.perKg <= 0:                        # checked twice already
        raise newException(ValueError, "corrupt rate for " & zone)
        ^

Nim 2.3.1, before.nim with {.raises: [].} added to shippingCost on line 28. The compiler also prints before.nim(28, 61) template/generic instantiation from here.

On trusted code the empty raises list is the contract, and the compiler checks it on every build.

8 of 8 runs without the skill, 0 of 8 with it

We measured this on a private benchmark task: a multi-module quote calculator with three bundled data tables compiled into the program. Each run used the pi coding agent in a sandbox, with or without the nim-error-handling skill, on DeepSeek V4.1 Flash and GPT-6.1 Sol, both at maximum reasoning. We counted the raise and assert sites reachable from the bundled-table initialisers over lexed source, so comments and strings are ignored, and not by grep. Both arms produced correct programs. Every run in both arms built and passed every check on output, error reporting and API. The difference is in the code the agent left behind. With the skill, it validated once, at the boundary, and wrote fewer raise paths and less dead code. In a 5-runs-per-arm subset, the trusted modules came to 55–94 lines with the skill and 96–170 without it.

The skill states the rule in one place: data the project ships and the compiler parses is already trusted, so its checks belong in the build, and run-time checks belong where outside input enters.

The sample is small: 8 runs per arm, mostly one model family, with GPT-6.1 Sol contributing 1 run per arm. The task stays private because it feeds a future leaderboard. Earlier results and method notes are on the benchmarks page. All code examples were compiled and run with Nim 2.3.1 on Linux amd64.

Checklist for your own code

  • Parse project-owned data at compile time with const and staticRead, and raise from the parser. A bad file then fails the build.
  • Delete run-time re-checks of that data. They cannot fire, so they only add untested raise paths.
  • Validate user input once, at the boundary, and return a distinct type that trusted procs require.
  • Mark trusted procs {.raises: [].}. A re-check added later becomes a compile error.
